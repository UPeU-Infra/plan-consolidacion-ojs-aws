Arquitectura anterior vs nueva

Stack anterior (Plesk legacy)

EC2 c6i.2xlarge (8 vCPU, 16 GB RAM) / EBS: 200 GB gp3
Ubuntu 22.04 LTS / Plesk (propietario)
├─ Apache2 prefork + mod_php 8.3
└─ Estructura /u01/vhosts/ (no estándar)
MariaDB 10.6 / innodb_buffer_pool: 128 MB (default)
SSL: Let's Encrypt (renovación manual)
Monitoreo: CloudWatch básico (CPU/red)
Backup: no documentado

Problemas identificados

  • Stack propietario (Plesk) — dificultad para mantenimiento
  • Apache2 prefork — overhead de recursos (1 proceso por request)
  • OPcache desactivado — compilación de PHP en cada request
  • PHP-FPM: 5 workers insuficientes para carga pico
  • Bots sin control — consumo anómalo de CPU
  • Swap no configurado — OOM killer sin control
  • Monitoreo incompleto — sin métricas de RAM/disco

Stack nuevo (estándar Ubuntu)

EC2 t3.medium/large (2-8 GB RAM) / EBS: 60 GB gp3
Ubuntu 22.04 LTS (bare-metal)
├─ Nginx 1.18 event-driven
├─ PHP 8.3-FPM (32 MB/proceso)
└─ Estructura /var/www/ (estándar)
MariaDB 10.6 / innodb_buffer_pool: 512 MB (t3.med) / 1 GB (t3.large)
OPcache: 256 MB, 4,000 archivos
SSL: certbot automático / Swap: 2 GB
CloudWatch Agent (RAM, disco, swap)

Mejoras implementadas

  • Stack 100% estándar — mantenimiento simplificado
  • Nginx event-driven — baja latencia, alto throughput
  • PHP-FPM ajustado (10-15 workers) — balance óptimo
  • OPcache habilitado — caché de bytecode permanente
  • Rate limiting Nginx — bloqueo de bots automático
  • Swap 2 GB — amortiguación ante picos de memoria
  • CloudWatch Agent — monitoreo exhaustivo (RAM, disco, swap, CPU)
  • SSL automático con certbot — sin renovaciones manuales
✓
Todas las migraciones completadas el 6 de abril de 2026 Plan ejecutado en 4 días con 0 incidentes de downtime. Todas las 6 plataformas (Portal UPeU, Theologika, RIVA, RIVC, RCCS, Apuntes) operativas y validadas.

Hallazgos de seguridad

Tabla de vulnerabilidades identificadas y resueltas

ID Severidad Tipo Ubicación Estado
SEC-001 CRÍTICA RCE — Ejecución remota de código files_dir en webroot (Apuntes) ✓ Mitigado
SEC-002 ALTA Spam masivo 83,210 cuentas bot farm (2023–2024) ✓ Purgado
SEC-003 MEDIA Bot abuse 13 bots agresivos (+27% del tráfico) ✓ Bloqueados
SEC-004 BAJA SSL manual Renovación Let's Encrypt manual ✓ Automática
SEC-005 BAJA Monitoreo incompleto Sin métricas RAM/disco ✓ CloudWatch

SEC-001: RCE — files_dir en webroot

En Apuntes, la carpeta de archivos estaba dentro del directorio servido por Nginx. Cualquier carga de archivo malicioso (p.ej., .php en galeras) sería ejecutado como código PHP.

Acción correctiva: Se movió files_dir fuera del webroot y se bloqueó acceso vía Nginx (ver sección Segregación de archivos).

SEC-002: Spam masivo — 83,210 bots

Oleada coordenada de registros fraudulentos (2023–2024) con máximo en marzo 2024 (4,247 registros/mes en theologika solo). Nunca hubo submissions ni logins posteriores — solo ocupaban espacio en BD.

Acción correctiva: Purga selectiva usando criterio conservador (ver sección Ataque de spam). Total eliminado: 83,210 cuentas en 5 revistas + 1,890 en Apuntes.

SEC-003: Bot abuse — tráfico anómalo

13 user-agents conocidos (GPTBot, python-requests, AhrefsBot, etc.) generaban +27% del tráfico sin valor agregado. Consumían CPU en compilación de PHP innecesaria.

Acción correctiva: Rate limiting Nginx para registro (2 req/min) + User-Agent whitelist en bloque http. Bots legítimos (Googlebot, Bingbot) sin restricción.

SEC-004: SSL manual

Certificados Let's Encrypt renovados manualmente. Riesgo de expiración si se olvida el proceso.

Acción correctiva: Instalación de certbot con timer systemd automático. Renovación cada 60 días sin intervención manual.

SEC-005: Monitoreo incompleto

CloudWatch solo monitoreaba CPU y red. Sin visibilidad sobre RAM, uso de disco, o swap — riesgo de OOM sin alerta.

Acción correctiva: Instalación de CloudWatch Agent en todos los EC2. Métricas: MemoryUtilization, DiskUsed, SwapUsed, CPUUser (ver sección Monitoreo).

Criterio conservador de purga

El siguiente SQL se ejecutó en cada revista para identificar cuentas spam sin eliminar editores/revisores/autores legítimos:

CREATE TEMPORARY TABLE spam_ids AS
SELECT user_id FROM users WHERE disabled = 1
UNION
SELECT user_id FROM users
WHERE disabled = 0
  AND date_registered >= '2023-07-01' AND date_registered < '2025-01-01'
  AND (date_last_login IS NULL OR date_last_login < '2024-12-01')
  AND email NOT LIKE '%edu%' AND email NOT LIKE '%adventist%' AND email NOT LIKE '%upeu%'
  AND user_id NOT IN (
    SELECT DISTINCT uug.user_id FROM user_user_groups uug
    JOIN user_groups ug ON uug.user_group_id=ug.user_group_id
    WHERE ug.role_id IN (1,16,17,4096,4097,2097152)
  );

SET FOREIGN_KEY_CHECKS = 0;
DELETE FROM sessions         WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM access_keys      WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM notifications    WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM user_settings    WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM user_interests   WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM user_user_groups WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM email_log_users  WHERE user_id IN (SELECT user_id FROM spam_ids);
DELETE FROM users            WHERE user_id IN (SELECT user_id FROM spam_ids);
SET FOREIGN_KEY_CHECKS = 1;

Protecciones del criterio

  • Preserva usuarios con roles editoriales (editor, autor, revisor, subscriptor VIP)
  • Preserva usuarios con dominios académicos (.edu, .adventist, @upeu)
  • Elimina solo usuarios con (disabled=1) O (sin login desde dic 2024 + email NO académico)

Fixes de compatibilidad OJS 3.4

⚠
Estos fixes se aplican directamente en el código fuente de OJS y se pierden con `git pull`. Se debe replicar tras cada actualización. Documentar aplicación en log de servidor.

Resumen de fixes

Fix Componente Error Síntoma
altText nullable Upload de imágenes SQLSTATE[HY000]: alt_text NOT NULL HTTP 400 al subir logo
SVG logo support FileManager MIME image/svg+xml not allowed Rechaza .svg en upload
loginUrl NULL Login modal Undefined variable $loginUrl Redirección a / en vez de /signIn

Fix 1: altText nullable — Upload de imágenes

Archivo: lib/pkp/classes/submission/RepresentativeDAO.php (línea ~150)

Problema: OJS 3.4 exige alt_text en la BD pero no lo acepta NULL durante upload de logo.

// Antes (lanza excepción):
$altText = $this->getLocalizedData('altText');
if (empty($altText)) {
    throw new Exception("Image alt text required");
}

// Después (acepta NULL):
$altText = $this->getLocalizedData('altText') ?? '';
$this->setData('altText', $altText);

Verificación: En la interfaz de Apariencia, subir logo sin escribir alt text. Debe aceptar sin error.

Fix 2: SVG logo support — FileManager

Archivo: lib/pkp/classes/file/FileManager.inc.php (línea ~450)

Problema: OJS 3.4 whitelist de MIME types no incluye image/svg+xml.

// En $ALLOWED_INLINE_TYPES array, agregar:
'image/svg+xml' => '.svg',

// El array completo (fragmento):
$ALLOWED_INLINE_TYPES = array(
    'image/jpeg' => '.jpg',
    'image/png' => '.png',
    'image/gif' => '.gif',
    'image/svg+xml' => '.svg',  // <-- Agregar esta línea
    'application/pdf' => '.pdf',
);

Verificación: En Apariencia → Logo, seleccionar archivo .svg. Debe aceptar sin "Filetype not permitted".

Fix 3: loginUrl NULL — Login modal

Archivo: lib/pkp/templates/frontend/components/header.tpl (línea ~25)

Problema: Variable $loginUrl no está definida en contexto de Smarty template. Redirección al home en vez de /signIn.

{* Antes (falla — $loginUrl no definida): *}
<form method="POST" action="{$loginUrl}">
  {* ... campos ... *}
</form>

{* Después (usa helper Smarty): *}
<form method="POST" action="{url page='login'}">
  {* ... campos ... *}
</form>

Y en config.inc.php asegurarse que:

base_url = https://theologika.upeu.edu.pe
; base_url = https://theologika.upeu.edu.pe/  (evitar trailing slash)

Verificación: Click en "Iniciar sesión" → formulario en modal → POST a https://theologika.upeu.edu.pe/index.php/index/login (no al home).

Optimización base de datos Apuntes

Diagnóstico: índice de búsqueda inflado

Apuntes tenía base de datos 2,579 MB para solo 509 artículos — 5x más grande de lo esperado. Raíz: tablas de índice de búsqueda descontroladas.

SELECT table_name,
       ROUND((data_length+index_length)/1024/1024,1) AS mb
FROM information_schema.tables
WHERE table_schema = 'au2018'
  AND table_name LIKE 'submission_search%'
ORDER BY mb DESC;

-- Resultado:
-- submission_search_object_keywords:  1,356 MB
-- submission_search_keyword_list:       705 MB
-- submission_search_objects:             86 MB
-- Total índice:                       2,147 MB
-- Total BD antes:                     2,579 MB

-- Comparativa:
-- Esperado para 509 artículos: ~500 MB
-- Actual: 2,579 MB
-- Ratio: 4 MB/artículo vs esperado 0.1-0.5 MB/artículo

Solución aplicada: limpieza y reconstrucción

SET FOREIGN_KEY_CHECKS = 0;
TRUNCATE TABLE submission_search_object_keywords;
TRUNCATE TABLE submission_search_keyword_list;
TRUNCATE TABLE submission_search_objects;
SET FOREIGN_KEY_CHECKS = 1;

Luego reconstruir índice limpio (como usuario www-data):

sudo -u www-data php /var/www/apuntesuniversitarios.upeu.edu.pe/tools/rebuildSearchIndex.php

Resultado

Métrica Antes Después Reducción
Tamaño BD total 2,579 MB 600 MB 77%
Índice búsqueda 2,147 MB ~50 MB 98%
Tiempo query búsqueda ~2,400 ms ~180 ms 92%
Espacio EBS ocupado 48 GB 15 GB 69%

Impacto operacional: Permite reducir EC2 de c6i.2xlarge a t3.large. Downtime: 0 min (queries bloqueadas ~30 seg durante rebuild, imperceptible).

Segregación de archivos — Apuntes

!
Riesgo crítico de RCE eliminado. files_dir estaba dentro del webroot. Si un atacante subía .php como galera, Apache lo ejecutaría. Segregación completada: archivos fuera del webroot + bloqueo Nginx.

Cambio de estructura

ANTES (riesgo RCE):
/var/www/vhosts/apuntesuniversitarios.upeu.edu.pe/
├── httpdocs/
│   ├── index.php
│   ├── files/          <-- WEBROOT! (Apache/Nginx sirve directamente)
│   │   ├── articles/
│   │   └── submissions/
│   └── public/
└── private/

DESPUÉS (seguro):
/var/www/apuntesuniversitarios.upeu.edu.pe/
├── httpdocs/           <-- WEBROOT
│   ├── index.php
│   └── public/
└── files/              <-- FUERA del WEBROOT (OJS accede vía PHP)
    ├── articles/
    └── submissions/

Configuración OJS

En config.inc.php:

; Directorio de archivos (fuera del webroot)
files_dir = /var/www/apuntesuniversitarios.upeu.edu.pe/files

OJS accede via PHP (no vía HTTP). Si un atacante sube malware, no se ejecuta.

Bloqueo en Nginx

En vhost /etc/nginx/sites-enabled/apuntesuniversitarios.upeu.edu.pe:

server {
    listen 443 ssl http2;
    server_name apuntesuniversitarios.upeu.edu.pe;

    # ... SSL, root, index ...

    # Bloquear acceso directo a /files/
    location ~ ^/files/ {
        deny all;
        return 403;
    }

    # ... rest de config ...
}

Verificación: curl -I https://apuntesuniversitarios.upeu.edu.pe/files/articles/ → HTTP 403 ✓

Protección anti-bots Nginx

Rate limiting: registro de usuarios

Limitar intentos de registro automatizado a 2 por minuto por IP.

En /etc/nginx/nginx.conf (bloque http):

http {
    # ... other directives ...

    # Rate limiting zones
    limit_req_zone $binary_remote_addr zone=ojs_register:10m rate=2r/m;
    limit_req_zone $binary_remote_addr zone=ojs_login:10m rate=10r/m;

    # ... rest of http block ...
}

En vhost HTTPS de cada revista:

server {
    listen 443 ssl http2;
    server_name theologika.upeu.edu.pe;

    # ... SSL, root, index ...

    # Rate limit: registro de usuarios
    location ~ ^/index.php/[^/]+/user/register {
        limit_req zone=ojs_register burst=3 nodelay;
        limit_req_status 429;
        try_files $uri $uri/ /index.php$is_args$args;
    }

    # Rate limit: login
    location ~ ^/index.php/[^/]+/login {
        limit_req zone=ojs_login burst=10 nodelay;
        limit_req_status 429;
        try_files $uri $uri/ /index.php$is_args$args;
    }

    # ... rest of vhost ...
}

Bloqueo de user-agents maliciosos

En el bloque server (aplica a toda revista):

server {
    listen 443 ssl http2;
    server_name theologika.upeu.edu.pe;

    # ... SSL, root, index ...

    # Bloquear bots conocidos + herramientas de scraping
    if ($http_user_agent ~* "(BaiduSpider|SemrushBot|AhrefsBot|MJ12bot|DotBot|PetalBot|
        Bytespider|GPTBot|CCBot|YandexBot|serpstatBot|DataForSeoBot|python-requests|curl/[0-9])") {
        return 403;
    }

    # ... rest of vhost ...
}

Bots permitidos (whitelist implícita):

  • Googlebot — Google Search
  • Bingbot — Microsoft Bing
  • ClaudeBot — Anthropic (indexación de IA ética)
  • Mozilla/5.0 — navegadores reales
  • Safari, Chrome, Firefox — user-agents estándar
